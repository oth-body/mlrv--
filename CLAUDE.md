# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

This repo is `oth-body/mlrv--`, a fork of `trentgill/mlrv2` — a Max/MSP live-sampling instrument for monome grid controllers, refactored by Trent Gill/Michael Felix from Brian Crabtree's original `mlr`. It contains two independent things:

- **`mlrv2/`** — the original Max/MSP patches. Fork history is byte-identical to upstream (confirmed via `git describe --tags HEAD` and a full `git log` diff against `trentgill/mlrv2`); treat this directory as a frozen reference, not something to edit.
- **`mlrv-pd/`** — a from-scratch Pure Data reimplementation of `mlrv2`'s behavior, started 2026-09-17. This is the active-development directory.

Neither this fork nor upstream carries a `LICENSE` file — see `mlrv-pd/NOTICE` for the provenance/licensing situation before adding one or redistributing anything.

## `mlrv2/` — original Max/MSP (reference only, not conventional source)

`.maxpat` files are JSON-serialized visual dataflow patches, not text source in any meaningful sense — reading them gives you object names, comments, and creation args, but not the actual wiring/control-flow (that requires opening them in Max itself). There is no build, lint, or test tooling for this directory, and none is possible without a licensed Max/MSP install. `code/serialosc.js` is the one real piece of code in this directory (monome device discovery over OSC) and is the reference for `mlrv-pd/patchers/serialosc.pd`'s reimplementation.

Known gap in the original: `gridcell.maxpat`/`metapattern.maxpat` use `xrecord~`/`xgroove~` from Thomas Grill's third-party **xsample** external, not stock Max — `mixer.maxpat` itself contains the comment `"xsample external not found"`, meaning the original may already run degraded on a current Max install.

## `mlrv-pd/` — Pure Data port (active work)

Requires Pure Data (`pd`, tested against 0.56.5). No GUI is needed for validation — everything below runs headless.

### Validating a `.pd` file

Pd abstractions only resolve their creation-argument substitutions (`$1`, `$2`, ...) when instantiated as an object inside a parent patch — opening a `.pd` file directly with `-open` will always throw spurious `argument number out of range` errors for any abstraction file with unresolved `$N` references. **Always validate through a wrapper/test patch that instantiates the file as an object with real arguments**, not by opening the file directly. The existing harnesses in `mlrv-pd/tests/` are the pattern to follow for new ones:

```sh
pd -nogui -stderr -path mlrv-pd/abstractions mlrv-pd/tests/test_play_loop.pd
pd -nogui -stderr -path mlrv-pd/patchers    mlrv-pd/tests/test_serialosc.pd
```

Clean (no output) means no load or runtime errors. `pd -nogui` does not exit on its own once loaded — wrap with `timeout N` when scripting.

### Non-obvious Pd behaviors that will bite you again in this codebase

1. **`$N` substitution requires backslash-escaping in the saved file (`\$1`, not `$1`), and means different things by box type.** A bare, unescaped `$N` anywhere in a `.pd` file fails immediately with `argument number out of range`, regardless of context. An escaped `\$N` in an **object** box resolves once, at instantiation, to the abstraction's real creation argument. An escaped `\$N` in a **message** box instead refers to the Nth atom of whatever message triggers that box *at runtime* — not the abstraction's creation argument at all. To get an abstraction's creation argument into a message box, route it through an object first (e.g. `[float \$1]`, banged) so the message box's `\$N` captures it as a genuine runtime atom. (Reference: Pd's own bundled `/usr/lib/pd/doc/2.control.examples/dollarsign2.pd`.)
2. **`oscformat` treats a symbol-leading message as a method call, not data**, unless the message is prefixed with the literal `list` selector (e.g. `list localhost 8000`, not `localhost 8000`). Symbol-leading messages without `set`/`format` selectors will otherwise error with `no method for '<symbol>'`.
3. **`oscparse` splits an OSC address into separate atoms on `/` and prefixes the whole output with the literal selector `list`** — it does not hand back `/serialosc/device` as one symbol. `/serialosc/device m0000-0000 grid 40921` arrives as `list serialosc device m0000-0000 grid 40921`. `[route /serialosc/device]` will never match this; you need a chain that strips one segment at a time: `[route list]` → `[route serialosc monome]` → `[route device add remove]` (and similarly `[route grid]` → `[route key]` for a 3-segment address like `/monome/grid/key`). This is the "nested routing" pattern demonstrated in Pd's own `/usr/lib/pd/doc/5.reference/osc-format-parse-help.pd`.
4. **`[trigger]`/`[t]` outlets fire right-to-left**, and this determines real execution order, not just output order. When an action depends on state set up by an earlier step (e.g. a `netsend` needs `connect host port` delivered before any data is sent to it), the step that must run *first* has to be wired to the **higher-numbered (rightmost) outlet** of the `t`. Getting this backwards doesn't error — it silently sends data to an unconnected socket, which just vanishes. This also applies to a single outlet fanned out to multiple destinations without an explicit `trigger`; don't assume an order there without checking — restructure through an explicit `t` instead of relying on it.
5. **`;` and `,` inside comment/message text must be backslash-escaped (`\;`, `\,`) in the saved file**, same as `$`. An unescaped `;` silently ends the current `#X` line and starts Pd trying to parse whatever follows as a brand-new object — producing a baffling `error: <next-word>: no such object` that has nothing to do with the actual bug. If you hit that error and didn't add an object by that name, check your most recently edited comment for a stray punctuation mark first.
6. **`netreceive`'s listening port is a creation-time argument only — it cannot be rebound at runtime.** Sending it a float post-creation doesn't change its port; Pd reads an unlabeled float there as an implicit `send` call (push data to a connected TCP client), which errors `'send' only works for TCP` in UDP mode. If a port needs computing (e.g. from another creation arg), do the arithmetic before the object is instantiated, or just require the literal final port as the creation arg directly — don't try to compute-then-rebind after the fact.
7. **Connection indices in a `.pd` file are positional, not stable identifiers — inserting a new `#X obj`/`#X msg`/`#X text` line anywhere except the very end silently renumbers every object after it, breaking every existing `#X connect` line that references those higher indices with no error at save time.** This has caused real regressions **three separate times** in this port so far (Turn 7's `[t b]` fix, Turn 8's tilt outlet, Turn 9's `[samplerate~]` wiring) — every time the file still "looked right" on a quick glance, and either failed on the next `pd -nogui` load or, worse, loaded cleanly while silently wiring the wrong objects together. Writing this rule down after the second occurrence did not prevent the third — **treat "re-read the file and recompute the index map before writing any new `#X connect` line" as mandatory on every single edit to an existing `.pd` file, not as a rule to apply only when something feels risky.** When adding a new object: always append it after the last existing `#X` line, never insert it between existing objects, even if that makes the visual layout less tidy — coordinates are cosmetic, position-in-file is load-bearing. Reload in `pd -nogui` immediately after every edit, not just at the end of a batch of edits. **Fourth occurrence, Turn 20 (`sample_voice~.pd`'s gain feature), a variant of the same root cause:** `#X` lines are processed strictly sequentially as the file loads, so a `#X connect` line referencing object N fails with `cannot connect to non-existing object` if it appears in the file *before* object N's own line — even with the index arithmetic correct. This bit when a new object was appended after the file's pre-existing `#X connect` block (matching "append at the end" too literally) while an *edited* connect line still sitting inside that earlier block was updated to reference it. The actual rule "append at the end" means: after the last existing **object** line (`#X obj`/`#X msg`/`#X text`/etc.) and *before* the first `#X connect` line — matching every file in this codebase's own objects-then-connects convention — not literally the last line of the file. New connects referencing a newly-appended object can go anywhere after that object's own line, including the true end of the file.
8. **A creation argument that must match some external runtime fact (like Pd's actual engine sample rate) is a bug waiting to happen — prefer querying that fact directly over asking the caller to supply it correctly.** `play_loop~.pd` originally took `sampleRate` as a required second creation argument; a test passed `44100` on a machine whose Pd engine actually runs at `48000` ([samplerate~] confirms the real value), and the loop played back audibly the wrong speed as a direct, fully-explained consequence — not a subtle bug, an 8%-off, perfectly-linear-growing error that took real diagnostic work to trace back to its root cause rather than just patching the symptom. Fixed by removing the argument entirely: `[loadbang] -> [samplerate~]` queries the true value once at load time. If you're about to add a creation argument and the "correct" value is something Pd itself already knows (sample rate, block size, etc.), query it instead of trusting the caller.
9. **`[pack]`'s creation arguments are not "default values with an inferred type" — a non-numeric argument must be the literal type keyword `s`/`symbol` or `p`/`pointer`, never a sample value like an array name.** `[pack 0 1 0 0 mlrv-sample-0]`, written to mean "four floats defaulting to 0/1/0/0 plus a symbol inlet defaulting to `mlrv-sample-0`", is invalid: Pd can't parse `mlrv-sample-0` as a type keyword or a number, silently defaults that inlet to **pointer** type, and the first real symbol sent there later crashes with `error: consistency check failed: gpointer_copy` — a confusing error far from its real cause. The correct form is `[pack 0 1 0 0 s]` (the `s` inlet's default value is simply empty; a real value arrives before the pack ever fires in practice, so this is rarely a problem once the syntax is right). Caught by a dedicated probe patch before writing this into a real abstraction, not discovered live in `file_poly.pd`/`sample_voice~.pd` itself — worth calling out as a case where testing the *design*, not just the finished file, paid off.
10. **An abstraction's outlets map to the `[abstraction]` object's outlets in the order of their X-coordinates, leftmost = outlet 0 — not by Y-position.** Probe-verified this session while debugging `file_poly.pd`: a `[outlet~]` at x=20 took outlet 0 and one at x=140 took outlet 1 (the earlier working assumption, that outlets sort by Y-position, was wrong and produced a swapped pair). Keep the outlet objects' x coordinates in the order you want externally — and remember gotcha 7: their *file* order still controls the `#X connect` index map, so these two orderings (file index and X position) are independent axes that both matter.
11. **`[tabwrite~]` writes exactly one pass per bang, and only when banged — a signal-less or un-banged tabwrite silently fills its array with zeros.** Three probe-verified facts from this session: (a) connected to a live signal but never banged, the array stays all zeros; (b) with a bang (which resets the write to index 0), it writes through the end of the array once and then stops — content is frozen, confirmed by reading the same cells at 200ms and 1500ms and getting identical values, so you can't rely on it wrapping or continuous capture; (c) connecting a control outlet (e.g. a `[t]` bang) into a tabwrite~'s signal inlet is legal and is exactly how it gets armed (`control-out → signal-in` on the same object). The classic trap: two `tabwrite~` objects sharing one array where the signal feeds one and the bang arms the other — the armed, signal-less one overwrites the array with zeros and the reads all come back 0 with no error. One array, one tabwrite~, both connections on it. (A `soundfiler` `write` from the array afterwards is the usual way to get the frozen content into a WAV — that's how `tests/test_file_poly.pd` captures its windows.)
12. **`[line~]` re-target ramps are relative to the current value — a retrigger while already at the target produces no visible change.** `sample_voice~.pd` fades in every play via `[line~]` being sent `1 5` (0→1 over 5ms); that only moves the signal when the voice is starting cold from 0. Re-triggering a voice that is already at full gain re-sends `1 5` but `line~` is already at 1, so there is no fade-in — a captured window armed in the same tick as a re-trigger comes out exact (this is why `file_poly.pd`'s capture2, a same-tick retrigger, matches the expected ramp with zero fade cells while capture1, a cold start, has a 5ms fade in its first ~220 cells that the test masks out).

13. **`[tabwrite name]`'s message is `value index` — the VALUE comes first, index second.** Assumed the reverse while building `mapping.pd`'s slot-length storage; `tabwrite` accepts the wrong order silently (no error — the value just lands in the wrong cell), which surfaced only as "slot 1 never plays" later in that same build (its length had been written into slot 0's cell). `[tabread name]` takes only the index and outputs the value. The store path in `mapping.pd` packs `(slot frames)` and flips the atoms with a `msg \$2 \$1` before the `tabwrite` so the pair arrives value-first.

14. **`[array set]/[array get]` are traps for small scalar state.** `[array set name]` replaces the whole array starting at index 0 — it does not write one cell and stop, so any partial state gets clobbered — and a direct message-box→`[table]` connection is illegal (Pd refuses to make it). Probe-settled alternative for scalar tables: declare `[table name N]` in-file and use `[tabwrite name]` (value/index order, gotcha 13) + `[tabread name]`. `mapping.pd` stores its 8 slot lengths exactly this way.

15. **`[pack]` emits on the HOT inlet (inlet 0) using the CURRENT stored values of the other float inlets — 0 until first set. There is no wait-for-all-inlets; the ordering is entirely on the wiring.** Feeding the hot inlet first therefore emits a message full of stale/zero values, and the real values arrive too late — this was the entire root cause of `mapping.pd`'s "silent triggers plus a wrong `play 0 0 0 0`" (handoff log Turn 12): the gate pack had `state` on the hot inlet before `x`/`y` arrived, so *every press acted on the previous press's slot*; the play pack had `slot` hot before rate/frames landed; the store pack had `frames` hot before `slot` landed (writing every load to index 0). Fix pattern: wire the **last-arriving** value to pack's inlet 0, the others to inlets 1..n, and re-order the emitted atoms with a `msg \$3 \$2 \$1`-style box back into the intended output order. Pairs with the established right-to-left firing of `t`/`unpack` (gotcha 4 / Protocol decisions note): the "last-arriving" value is the one on the leftmost source outlet.

16. **`[send~]`/`[receive~]` across an abstraction boundary add exactly one DSP block of latency** — the receiver hears the previous block's signal, not the current one. Measured empirically on `master.pd` (Turn 13): the `receive~ fxout` capture lagged the direct signal path by exactly 64 samples (= one DSP block at this machine's 48kHz sample rate with default block size 64). The fx return bus (`fxin`) also lags one block, but this is inaudible in practice because DC/gain signals are immune and real FX (reverb/delay) add far more inherent latency. Direct signal connections (outlet~ → inlet~) never have this lag. `throw~/catch~` have the same cross-boundary latency (not empirically verified in this codebase; the plan notes this as a possible alternative but both options share the property).

17. **`[tabwrite~]` with a single creation argument has ONE inlet that is both signal and control** — there is no separate inlet 1 for bang-to-arm. The hybrid inlet accepts the signal to record (on its signal side) and a bang to start recording from index 0 (on its message side); both connections land on inlet 0. Wiring a trigger's bang outlet into "inlet 1" produces a `connection failed (trigger->tabwrite~)` error at load time. This was discovered the hard way building `test_master.pd`: the mapping test already does this correctly (`connect 21 0 23 0` — bang into inlet 0 alongside the signal, not inlet 1), but the pattern wasn't obvious until the error pointed at it.

18. **A dynamic `\; $1 ...` send only substitutes `$1` when it arrives as a proper message — a bare symbol fails.** `makefilename`'s raw output (bare `mlrv-sample-3`) into `\; $1 resize 64` errors `$1: not enough arguments supplied` and sends nothing; routing through `[symbol]` first (or prefixing `list`) makes the identical message work. Same family as gotcha 2 (symbol-leading messages losing their list-ness). `[tabwrite]` (control) does support `set <array>` to re-point at runtime (probed), so one shared writer can serve many arrays; `[uzi]` does not exist in vanilla Pd 0.56.5 at all.

19. **Array `resize` retains surviving cells and zero-fills grown cells — resize alone never silences anything.** Probed: fill → `resize 4` → `resize 16` keeps old values in 0..3, reads 0 in 4..15. `file_poly.pd`'s `unload` therefore does resize-1 → write 0 at cell 0 → resize-64 (one explicit zero plus grow-zero-fill). Related design rule: occupancy queries must read **tracked** state, not live `[array size]` — an unloaded slot's physical size (64) is nonzero, so a live-size query re-reports it as loaded and downstream consumers (mapping.pd) resurrect it. `mlrv-fplen` tracks last-loaded frames (0 = empty) instead.

20. **`phasor~` handles a negative frequency correctly, including wrapping cleanly across the 0/1 phase boundary in either direction — and this makes reverse playback "free" for anything already built on the `phase → *~ range → +~ start → tabread4~` pattern.** Probed three separate facts before relying on any of them: (1) `phasor~ -10` produces a clean descending 0.8→0.6→...→0→(wrap) ramp, not silence or a stuck value; (2) after an explicit phase-0 reset, sample-level capture via `tabwrite~` showed sample[0]=0, sample[1]=0.999792 at freq -10Hz/48000sr — phase decrements below 0 and wraps to just-under-1 on the very next sample, it does not go negative/unwrapped; (3) `tabread4`'s 4-point interpolation clamps at negative/near-zero indices (constant output) rather than crashing or reading garbage, so the mirrored seam artifact at the low end in reverse mode is the same class of cosmetic known-limitation as the existing high-end seam, not a new crash risk. Net effect on `play_loop~.pd`: its existing bang-retrigger-to-phase-0 mechanism, completely unchanged, already produces correct reverse playback when given a negative `rate` — the first captured sample after a reverse retrigger reads the loop-start value for exactly one sample (a single-sample artifact, same category as the interpolation seam) before jumping to loop-end and descending cleanly from there. Verified end-to-end against real loaded audio through the actual abstraction, not just `phasor~` in isolation: `mlrv-pd/tests/run_play_loop_reverse_test.sh` (correlation 1.000000 against the reversed ramp, mean error 0.001%). Also confirmed the whole call chain leaves `rate` unclamped: `sample_voice~.pd`'s unpack/pack reorder and `file_poly.pd`'s `play`/`playv` dispatch apply `max 0`/`min 7` only to the slot number, never to rate — reverse playback needed zero plumbing changes anywhere, it was a caller-convention gap, not a missing feature.

21. **A `[float]` store on the query path must be written silently (right inlet) and read by bang (left inlet) — getting either wrong corrupts state or sprays spurious reports.** Two real bugs from building `mixer.pd`'s query, both caught by its suite, not inspection: (a) wiring the slot number into the store's *left* inlet overwrote every gain with its own slot index (query then reported `vol 1 1`, `vol 2 2` — correct-looking for slot 1, wrong everywhere else); the store needs a bang there, i.e. a `[t b f]` that fans the slot const to the pack's cold inlet and a bang to the store. (b) Tapping control receipts into the store's *left* inlet re-emitted every value, and that emission fired the report pack with a stale cold slot — every `vol`/`send` set leaked a bogus query-shaped line out the info outlet. Right inlet stores silently (the `slot_holder` pattern from Turn 11); left inlet is bang-to-read only. The same rule in one line: stores never sit on a hot inlet, and nothing downstream of a store may fire on a store-write.

### Protocol decisions specific to this port

- **No `monome-device` external dependency.** `serialosc.pd` talks to the `serialosc` daemon directly over UDP (`netsend`/`netreceive` with `-u -b`, `oscformat`/`oscparse`) against the wire protocol `mlrv2/code/serialosc.js` documents: daemon on `127.0.0.1:12002`, `/serialosc/list` + `/serialosc/notify` to discover/subscribe, `/serialosc/device` replies give each device's own OSC port, and `/sys/port` + `/sys/prefix` sent to that device's port complete the handshake.
- **No `port + 12288` offset scheme.** The original `serialosc.js` computes its listen port as `arguments[0] + 12288`, purely as its own internal bookkeeping convention — the `serialosc` daemon itself doesn't require or care about this offset. This port drops it: `serialosc.pd`'s port creation argument is the literal port to bind and advertise, full stop (see gotcha 6 above for why the offset can't be replicated faithfully in Pd anyway).
- **`play_loop~.pd`** is the shared loop-playback abstraction every sample voice reuses: `phasor~` (0–1 ramp) → scaled into `[loopStart, loopEnd)` via control-rate arithmetic → `tabread4~`. Its single control inlet takes either `bang` (retrigger from loop start) or a 3-element list `rate loopEndSamples loopStartSamples` for an atomic parameter update — this relies on Pd's `unpack` firing right-to-left, which is why the list argument order matters and isn't arbitrary. Known limitation, undocumented workaround: `tabread4~`'s 4-point interpolation window can read ~2 samples outside the loop bounds at the seam (no crossfade).

### Testing against a fake serialosc daemon

`mlrv-pd/tests/fake_serialosc.py` is a stdlib-only Python fixture that stands in for the real `serialosc` daemon + a grid device (real `serialosc` isn't packaged for this machine's distro and isn't installed). `mlrv-pd/tests/run_handshake_e2e.sh` runs it against `serialosc.pd` and asserts on both sides' logs — this is the actual regression test for anything touching `serialosc.pd`'s network behavior, not just a clean `pd -nogui` load. Run it after any change to that file:

```sh
mlrv-pd/tests/run_handshake_e2e.sh   # exit 0 and 7/7 PASS lines means it's still correct
```

Trust this script's actual exit code, not any "verified" claim written in a comment inside `serialosc.pd` — an earlier version of that file shipped with a confidently-worded but false verification claim (the script it referenced had a path bug and had never actually been run successfully). If you update `serialosc.pd`'s behavior, update and rerun this script in the same change, not after.

### Current implementation state

`play_loop~.pd`, `serialosc.pd` (discovery + handshake + grid-key routing + LED output + tilt input), and `grid.pd` (thin `x y level` LED-display translator) exist. Every file has now been verified against either real hardware or real, non-trivial content — there is no longer a "verified against fake data only" item.

`serialosc.pd` is confirmed against **real hardware, bidirectionally, under sustained load**: a physically connected monome 64 grid (serial `m64-0865`) — specifically a **greyscale/varibright grid with a tilt sensor**, confirmed by reading `serialosc`'s own source, not assumed — round-tripped a full 64-key sweep of real key presses into real LED output, with the LEDs visually confirmed lit, plus a continuous live stream of real tilt/accelerometer data while the grid was physically moved. It also passes the software-only `run_handshake_e2e.sh` suite against the fake daemon fixture. `/serialosc/add`/`/serialosc/remove` correctly re-trigger a rescan without crashing (their payload carries the same id/type/port triple as `/serialosc/device`, confirmed against the real daemon, and is safely discarded via `[t b]` rather than fed directly into a type-sensitive object).

`grid.pd`'s passthrough behavior is verified in isolation and by composition (`mlrv-pd/tests/grid_echo_test.pd`), not by a fresh live key-press session — a stated judgment call given how strong the compositional evidence already was.

`play_loop~.pd` no longer takes a `sampleRate` creation argument — see gotcha #8 below for why, and `mlrv-pd/tests/run_play_loop_audio_test.sh` for the real-audio verification (linear-ramp WAV fixture, captured output checked against the known-exact expected values: correlation 1.000000, mean error 0.003% of full-scale, perfectly monotonic).

**Reverse playback (Turn 20, per-voice sample parameters step 1) needed zero code changes anywhere in the pipeline** — see gotcha #20 for the full probe trail. A negative `rate` sent through the existing `rate loopEndSamples loopStartSamples` list already plays correctly backward, verified against real loaded audio (`mlrv-pd/tests/run_play_loop_reverse_test.sh`), and is unclamped all the way from `file_poly.pd`'s `play`/`playv` dispatch through `sample_voice~.pd` down to `play_loop~.pd` itself. This is a caller-convention capability, not a new feature — `mapping.pd` doesn't yet expose any grid gesture that sends a negative rate, so it isn't reachable from the grid yet.

**Pitch (Turn 20, step 2): new standalone `mlrv-pd/abstractions/semitones_to_rate.pd`** — one inlet (float semitones) → `[expr pow(2, $f1/12.)]` → one outlet (rate multiplier), matching `plx.maxpat`'s own formula exactly. Verified against 6 known values via `mlrv-pd/tests/run_semitones_to_rate_test.sh`. Deliberately a pure positive multiplier with no opinion about direction — a caller combines it with reverse's negative sign. Not yet wired into any caller.

**Per-voice gain (Turn 20, step 3): `sample_voice~.pd` now accepts a `gain <value>` message** (route grew from `route bang` to `route bang gain`), replacing the previously-hardcoded fade-in target of `1`. `gain` sets a stored per-trigger target (a `[float 1]`, default 1.0, cold-set) that the next play trigger's 5ms fade-in ramps to — it does not retarget an already-sounding voice, by design (that's a channel-fader job, which belongs to `mixer.pd`'s per-voice `vol`/`send` once wired in, not duplicated here). Verified against real captured audio: default (unset) gain plateau matches the pre-change behavior exactly, `gain 0.5` plateau is exactly half (`mlrv-pd/tests/run_sample_voice_gain_test.sh`). Building this hit two real bugs, both self-inflicted and both fixed the same session: (1) an unescaped comma in a new comment broke the parse (gotcha #5) with a baffling `error: canvas: no method for 'never'`; (2) a new object appended after the file's existing `#X connect` block, referenced by an edited connect line still sitting inside that earlier block, failed with `cannot connect to non-existing object` — connect lines are processed sequentially as the file loads, so any object they reference must already appear earlier in the file, not just have the "right" index. See gotcha #7's expanded note below.

**Pitch composition (Turn 21): `sample_voice~.pd` now also accepts `pitch <semitones>`** (route grew again, to `route bang gain pitch`), multiplying the play list's `rate` by `semitones_to_rate`'s output at each play trigger — composes with `rate`'s own sign, so reverse + pitch-shifted-reverse both work without special-casing. Unlike gain, this needed no separate store-plus-bang mechanism: `[semitones_to_rate]`'s output feeds a `[* 1]`'s cold inlet directly, and rate's own per-trigger arrival (already firing last relative to end/start, per the existing right-to-left unpack order) triggers the multiply's hot inlet naturally. `[* 1]`'s creation arg was probe-verified to seed the cold inlet to 1.0 (no shift) before any pitch message arrives. Verified against real captured audio: `mlrv-pd/tests/run_sample_voice_pitch_test.sh` — `pitch 12` (one octave) produces a read position that sweeps the array twice within one capture window (correlation 1.000000 against the analytically-derived double-speed wrapped ramp), and is confirmed distinct from the unpitched trace (correlation 0.23 against it), ruling out a no-op.

**`file_poly.pd` now exposes both per-voice, reachable from its top-level message interface**: `gain <voice 1-4> <value>` and `pitch <voice 1-4> <semitones>` (route grew from 7 to 9 matched symbols — outlets 7/8 — confirmed the old reject outlet, 7, was unconnected to anything before this change, so nothing needed rewiring because of the new outlet count). Built via a new builder script, `mlrv-pd/tests/builders/extend_file_poly_gain_pitch.py`, mirroring the peer session's `extend_file_poly.py` pattern (assert-then-append, never hand-edited given the file's size). Design: `unpack f f` on `voice value`, right-to-left firing puts `value` into a shared `[float 0]`'s cold inlet before `voice` fires last and triggers `[route 1 2 3 4]`; the matching outlet's bare bang (a lone number with nothing trailing it always emits one) re-reads the stored value into that voice's own `"<keyword> $1"` message. This file does no arithmetic on the value itself, only dispatch — the actual gain/pitch math lives entirely in `sample_voice~.pd`. Verified end-to-end against real captured audio through the real message interface (not just sample_voice~.pd in isolation): `mlrv-pd/tests/run_file_poly_gain_pitch_test.sh`. **Still not reachable from `mapping.pd`/the grid** — no gesture sends any of `gain`/`pitch`/negative-rate yet; that remains the one open item in the Per-Voice Sample Parameters doc's wiring gap, now narrower than before.

`mixer.pd` is **built and verified** (Turn 15, Phase 3.2). Same design as Turn 14 planned: 4 `inlet~` (pre-fader voice audio, inlets 0-3) + 1 control `inlet` (inlet 4 — inlet order is by x-coordinate per gotcha 10, so the control inlet's object sits at the highest x) taking `vol <v 0..3> <gain>` / `send <v 0..3> <level>`, both `line~ 10` ramped, dispatch `route vol send` → `route 0 1 2 3`. Dry sum (`voice*vol`, 3×`+~` chain) → `outlet~` (feeds `master.pd`). Wet sum (`voice*vol*send`, post-fader tap) → `send~ fxout` (feeds `master.pd`'s `receive~ fxin`). Vols default to 1.0 via a loadbang-seeded `line~` target (mirrors the original's `vol_fade`'s `loadmess 1.`); sends default to 0 (line~'s own unset value, no seeding needed). Mute is `vol <v> 0`; pan deferred (mono master). `mlrv-pd/tests/run_mixer_test.sh` is its regression suite: 4 fixtures (2 distinct-level consts, 2 distinct-peak ramps) all sized to exactly one loop period so a full-window capture's *mean* is phase-independent regardless of exactly when in real time each capture started — sidesteps tracking exact playback phase across independently-scheduled real-time triggers while a wrong voice→gain mapping still breaks the expected sum immediately. Two dry windows with different gains (mean 20000 → 12000) rule out a coincidental compensating-error pass; the wet window uses a DC (const) voice specifically so it's exact even across the one-block `send~`/`receive~` lag (gotcha 16) — shifting a constant in time doesn't change its value. All checks pass at exact-integer tolerances (±6 out of a 32768 range).
