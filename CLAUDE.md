# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository overview

This repo is `oth-body/mlrv--`, a fork of `trentgill/mlrv2` — a Max/MSP live-sampling instrument for monome grid controllers, refactored by Trent Gill/Michael Felix from Brian Crabtree's original `mlr`. It contains two independent things:

- **`mlrv2/`** — the original Max/MSP patches. Fork history is byte-identical to upstream (confirmed via `git describe --tags HEAD` and a full `git log` diff against `trentgill/mlrv2`); treat this directory as a frozen reference, not something to edit.
- **`mlrv-pd/`** — a from-scratch Pure Data reimplementation of `mlrv2`'s behavior, started 2026-09-17. This is the active-development directory.

Neither this fork nor upstream carries a `LICENSE` file — see `mlrv-pd/NOTICE` for the provenance/licensing situation before adding one or redistributing anything.

## `mlrv2/` — original Max/MSP (reference only, not conventional source)

`.maxpat` files are JSON-serialized visual dataflow patches, not text source in any meaningful sense — reading them gives you object names, comments, and creation args, but not the actual wiring/control-flow (that requires opening them in Max itself). There is no build, lint, or test tooling for this directory, and none is possible without a licensed Max/MSP install. `code/serialosc.js` is the one real piece of code in this directory (monome device discovery over OSC) and is the reference for `mlrv-pd/patchers/serialosc.pd`'s reimplementation.

Known gap in the original: `gridcell.maxpat`/`metapattern.maxpat` use `xrecord~`/`xgroove~` from Thomas Grill's third-party **xsample** external, not stock Max — `mixer.maxpat` itself contains the comment `"xsample external not found"`, meaning the original may already run degraded on a current Max install.

## `mlrv-pd/` — Pure Data port (active work)

Requires Pure Data (`pd`, tested against 0.56.5). No GUI is needed for validation — everything below runs headless.

### Validating a `.pd` file

Pd abstractions only resolve their creation-argument substitutions (`$1`, `$2`, ...) when instantiated as an object inside a parent patch — opening a `.pd` file directly with `-open` will always throw spurious `argument number out of range` errors for any abstraction file with unresolved `$N` references. **Always validate through a wrapper/test patch that instantiates the file as an object with real arguments**, not by opening the file directly. The existing harnesses in `mlrv-pd/tests/` are the pattern to follow for new ones:

```sh
pd -nogui -stderr -path mlrv-pd/abstractions mlrv-pd/tests/test_play_loop.pd
pd -nogui -stderr -path mlrv-pd/patchers    mlrv-pd/tests/test_serialosc.pd
```

Clean (no output) means no load or runtime errors. `pd -nogui` does not exit on its own once loaded — wrap with `timeout N` when scripting.

### Non-obvious Pd behaviors that will bite you again in this codebase

1. **`$N` substitution requires backslash-escaping in the saved file (`\$1`, not `$1`), and means different things by box type.** A bare, unescaped `$N` anywhere in a `.pd` file fails immediately with `argument number out of range`, regardless of context. An escaped `\$N` in an **object** box resolves once, at instantiation, to the abstraction's real creation argument. An escaped `\$N` in a **message** box instead refers to the Nth atom of whatever message triggers that box *at runtime* — not the abstraction's creation argument at all. To get an abstraction's creation argument into a message box, route it through an object first (e.g. `[float \$1]`, banged) so the message box's `\$N` captures it as a genuine runtime atom. (Reference: Pd's own bundled `/usr/lib/pd/doc/2.control.examples/dollarsign2.pd`.)
2. **`oscformat` treats a symbol-leading message as a method call, not data**, unless the message is prefixed with the literal `list` selector (e.g. `list localhost 8000`, not `localhost 8000`). Symbol-leading messages without `set`/`format` selectors will otherwise error with `no method for '<symbol>'`.
3. **`oscparse` splits an OSC address into separate atoms on `/` and prefixes the whole output with the literal selector `list`** — it does not hand back `/serialosc/device` as one symbol. `/serialosc/device m0000-0000 grid 40921` arrives as `list serialosc device m0000-0000 grid 40921`. `[route /serialosc/device]` will never match this; you need a chain that strips one segment at a time: `[route list]` → `[route serialosc monome]` → `[route device add remove]` (and similarly `[route grid]` → `[route key]` for a 3-segment address like `/monome/grid/key`). This is the "nested routing" pattern demonstrated in Pd's own `/usr/lib/pd/doc/5.reference/osc-format-parse-help.pd`.
4. **`[trigger]`/`[t]` outlets fire right-to-left**, and this determines real execution order, not just output order. When an action depends on state set up by an earlier step (e.g. a `netsend` needs `connect host port` delivered before any data is sent to it), the step that must run *first* has to be wired to the **higher-numbered (rightmost) outlet** of the `t`. Getting this backwards doesn't error — it silently sends data to an unconnected socket, which just vanishes. This also applies to a single outlet fanned out to multiple destinations without an explicit `trigger`; don't assume an order there without checking — restructure through an explicit `t` instead of relying on it.
5. **`;` and `,` inside comment/message text must be backslash-escaped (`\;`, `\,`) in the saved file**, same as `$`. An unescaped `;` silently ends the current `#X` line and starts Pd trying to parse whatever follows as a brand-new object — producing a baffling `error: <next-word>: no such object` that has nothing to do with the actual bug. If you hit that error and didn't add an object by that name, check your most recently edited comment for a stray punctuation mark first.
6. **`netreceive`'s listening port is a creation-time argument only — it cannot be rebound at runtime.** Sending it a float post-creation doesn't change its port; Pd reads an unlabeled float there as an implicit `send` call (push data to a connected TCP client), which errors `'send' only works for TCP` in UDP mode. If a port needs computing (e.g. from another creation arg), do the arithmetic before the object is instantiated, or just require the literal final port as the creation arg directly — don't try to compute-then-rebind after the fact.
7. **Connection indices in a `.pd` file are positional, not stable identifiers — inserting a new `#X obj`/`#X msg`/`#X text` line anywhere except the very end silently renumbers every object after it, breaking every existing `#X connect` line that references those higher indices with no error at save time.** This has caused real regressions **three separate times** in this port so far (Turn 7's `[t b]` fix, Turn 8's tilt outlet, Turn 9's `[samplerate~]` wiring) — every time the file still "looked right" on a quick glance, and either failed on the next `pd -nogui` load or, worse, loaded cleanly while silently wiring the wrong objects together. Writing this rule down after the second occurrence did not prevent the third — **treat "re-read the file and recompute the index map before writing any new `#X connect` line" as mandatory on every single edit to an existing `.pd` file, not as a rule to apply only when something feels risky.** When adding a new object: always append it after the last existing `#X` line, never insert it between existing objects, even if that makes the visual layout less tidy — coordinates are cosmetic, position-in-file is load-bearing. Reload in `pd -nogui` immediately after every edit, not just at the end of a batch of edits. **Fourth occurrence, Turn 20 (`sample_voice~.pd`'s gain feature), a variant of the same root cause:** `#X` lines are processed strictly sequentially as the file loads, so a `#X connect` line referencing object N fails with `cannot connect to non-existing object` if it appears in the file *before* object N's own line — even with the index arithmetic correct. This bit when a new object was appended after the file's pre-existing `#X connect` block (matching "append at the end" too literally) while an *edited* connect line still sitting inside that earlier block was updated to reference it. The actual rule "append at the end" means: after the last existing **object** line (`#X obj`/`#X msg`/`#X text`/etc.) and *before* the first `#X connect` line — matching every file in this codebase's own objects-then-connects convention — not literally the last line of the file. New connects referencing a newly-appended object can go anywhere after that object's own line, including the true end of the file.
8. **A creation argument that must match some external runtime fact (like Pd's actual engine sample rate) is a bug waiting to happen — prefer querying that fact directly over asking the caller to supply it correctly.** `play_loop~.pd` originally took `sampleRate` as a required second creation argument; a test passed `44100` on a machine whose Pd engine actually runs at `48000` ([samplerate~] confirms the real value), and the loop played back audibly the wrong speed as a direct, fully-explained consequence — not a subtle bug, an 8%-off, perfectly-linear-growing error that took real diagnostic work to trace back to its root cause rather than just patching the symptom. Fixed by removing the argument entirely: `[loadbang] -> [samplerate~]` queries the true value once at load time. If you're about to add a creation argument and the "correct" value is something Pd itself already knows (sample rate, block size, etc.), query it instead of trusting the caller.
9. **`[pack]`'s creation arguments are not "default values with an inferred type" — a non-numeric argument must be the literal type keyword `s`/`symbol` or `p`/`pointer`, never a sample value like an array name.** `[pack 0 1 0 0 mlrv-sample-0]`, written to mean "four floats defaulting to 0/1/0/0 plus a symbol inlet defaulting to `mlrv-sample-0`", is invalid: Pd can't parse `mlrv-sample-0` as a type keyword or a number, silently defaults that inlet to **pointer** type, and the first real symbol sent there later crashes with `error: consistency check failed: gpointer_copy` — a confusing error far from its real cause. The correct form is `[pack 0 1 0 0 s]` (the `s` inlet's default value is simply empty; a real value arrives before the pack ever fires in practice, so this is rarely a problem once the syntax is right). Caught by a dedicated probe patch before writing this into a real abstraction, not discovered live in `file_poly.pd`/`sample_voice~.pd` itself — worth calling out as a case where testing the *design*, not just the finished file, paid off.
10. **An abstraction's outlets map to the `[abstraction]` object's outlets in the order of their X-coordinates, leftmost = outlet 0 — not by Y-position.** Probe-verified this session while debugging `file_poly.pd`: a `[outlet~]` at x=20 took outlet 0 and one at x=140 took outlet 1 (the earlier working assumption, that outlets sort by Y-position, was wrong and produced a swapped pair). Keep the outlet objects' x coordinates in the order you want externally — and remember gotcha 7: their *file* order still controls the `#X connect` index map, so these two orderings (file index and X position) are independent axes that both matter.
11. **`[tabwrite~]` writes exactly one pass per bang, and only when banged — a signal-less or un-banged tabwrite silently fills its array with zeros.** Three probe-verified facts from this session: (a) connected to a live signal but never banged, the array stays all zeros; (b) with a bang (which resets the write to index 0), it writes through the end of the array once and then stops — content is frozen, confirmed by reading the same cells at 200ms and 1500ms and getting identical values, so you can't rely on it wrapping or continuous capture; (c) connecting a control outlet (e.g. a `[t]` bang) into a tabwrite~'s signal inlet is legal and is exactly how it gets armed (`control-out → signal-in` on the same object). The classic trap: two `tabwrite~` objects sharing one array where the signal feeds one and the bang arms the other — the armed, signal-less one overwrites the array with zeros and the reads all come back 0 with no error. One array, one tabwrite~, both connections on it. (A `soundfiler` `write` from the array afterwards is the usual way to get the frozen content into a WAV — that's how `tests/test_file_poly.pd` captures its windows.)
12. **`[line~]` re-target ramps are relative to the current value — a retrigger while already at the target produces no visible change.** `sample_voice~.pd` fades in every play via `[line~]` being sent `1 5` (0→1 over 5ms); that only moves the signal when the voice is starting cold from 0. Re-triggering a voice that is already at full gain re-sends `1 5` but `line~` is already at 1, so there is no fade-in — a captured window armed in the same tick as a re-trigger comes out exact (this is why `file_poly.pd`'s capture2, a same-tick retrigger, matches the expected ramp with zero fade cells while capture1, a cold start, has a 5ms fade in its first ~220 cells that the test masks out).

13. **`[tabwrite name]`'s message is `value index` — the VALUE comes first, index second.** Assumed the reverse while building `mapping.pd`'s slot-length storage; `tabwrite` accepts the wrong order silently (no error — the value just lands in the wrong cell), which surfaced only as "slot 1 never plays" later in that same build (its length had been written into slot 0's cell). `[tabread name]` takes only the index and outputs the value. The store path in `mapping.pd` packs `(slot frames)` and flips the atoms with a `msg \$2 \$1` before the `tabwrite` so the pair arrives value-first.

14. **`[array set]/[array get]` are traps for small scalar state.** `[array set name]` replaces the whole array starting at index 0 — it does not write one cell and stop, so any partial state gets clobbered — and a direct message-box→`[table]` connection is illegal (Pd refuses to make it). Probe-settled alternative for scalar tables: declare `[table name N]` in-file and use `[tabwrite name]` (value/index order, gotcha 13) + `[tabread name]`. `mapping.pd` stores its 8 slot lengths exactly this way.

15. **`[pack]` emits on the HOT inlet (inlet 0) using the CURRENT stored values of the other float inlets — 0 until first set. There is no wait-for-all-inlets; the ordering is entirely on the wiring.** Feeding the hot inlet first therefore emits a message full of stale/zero values, and the real values arrive too late — this was the entire root cause of `mapping.pd`'s "silent triggers plus a wrong `play 0 0 0 0`" (handoff log Turn 12): the gate pack had `state` on the hot inlet before `x`/`y` arrived, so *every press acted on the previous press's slot*; the play pack had `slot` hot before rate/frames landed; the store pack had `frames` hot before `slot` landed (writing every load to index 0). Fix pattern: wire the **last-arriving** value to pack's inlet 0, the others to inlets 1..n, and re-order the emitted atoms with a `msg \$3 \$2 \$1`-style box back into the intended output order. Pairs with the established right-to-left firing of `t`/`unpack` (gotcha 4 / Protocol decisions note): the "last-arriving" value is the one on the leftmost source outlet.

16. **`[send~]`/`[receive~]` across an abstraction boundary add exactly one DSP block of latency** — the receiver hears the previous block's signal, not the current one. Measured empirically on `master.pd` (Turn 13): the `receive~ fxout` capture lagged the direct signal path by exactly 64 samples (= one DSP block at this machine's 48kHz sample rate with default block size 64). The fx return bus (`fxin`) also lags one block, but this is inaudible in practice because DC/gain signals are immune and real FX (reverb/delay) add far more inherent latency. Direct signal connections (outlet~ → inlet~) never have this lag. `throw~/catch~` have the same cross-boundary latency (not empirically verified in this codebase; the plan notes this as a possible alternative but both options share the property).

17. **`[tabwrite~]` with a single creation argument has ONE inlet that is both signal and control** — there is no separate inlet 1 for bang-to-arm. The hybrid inlet accepts the signal to record (on its signal side) and a bang to start recording from index 0 (on its message side); both connections land on inlet 0. Wiring a trigger's bang outlet into "inlet 1" produces a `connection failed (trigger->tabwrite~)` error at load time. This was discovered the hard way building `test_master.pd`: the mapping test already does this correctly (`connect 21 0 23 0` — bang into inlet 0 alongside the signal, not inlet 1), but the pattern wasn't obvious until the error pointed at it.

18. **A dynamic `\; $1 ...` send only substitutes `$1` when it arrives as a proper message — a bare symbol fails.** `makefilename`'s raw output (bare `mlrv-sample-3`) into `\; $1 resize 64` errors `$1: not enough arguments supplied` and sends nothing; routing through `[symbol]` first (or prefixing `list`) makes the identical message work. Same family as gotcha 2 (symbol-leading messages losing their list-ness). `[tabwrite]` (control) does support `set <array>` to re-point at runtime (probed), so one shared writer can serve many arrays; `[uzi]` does not exist in vanilla Pd 0.56.5 at all.

19. **Array `resize` retains surviving cells and zero-fills grown cells — resize alone never silences anything.** Probed: fill → `resize 4` → `resize 16` keeps old values in 0..3, reads 0 in 4..15. `file_poly.pd`'s `unload` therefore does resize-1 → write 0 at cell 0 → resize-64 (one explicit zero plus grow-zero-fill). Related design rule: occupancy queries must read **tracked** state, not live `[array size]` — an unloaded slot's physical size (64) is nonzero, so a live-size query re-reports it as loaded and downstream consumers (mapping.pd) resurrect it. `mlrv-fplen` tracks last-loaded frames (0 = empty) instead.

20. **`phasor~` handles a negative frequency correctly, including wrapping cleanly across the 0/1 phase boundary in either direction — and this makes reverse playback "free" for anything already built on the `phase → *~ range → +~ start → tabread4~` pattern.** Probed three separate facts before relying on any of them: (1) `phasor~ -10` produces a clean descending 0.8→0.6→...→0→(wrap) ramp, not silence or a stuck value; (2) after an explicit phase-0 reset, sample-level capture via `tabwrite~` showed sample[0]=0, sample[1]=0.999792 at freq -10Hz/48000sr — phase decrements below 0 and wraps to just-under-1 on the very next sample, it does not go negative/unwrapped; (3) `tabread4`'s 4-point interpolation clamps at negative/near-zero indices (constant output) rather than crashing or reading garbage, so the mirrored seam artifact at the low end in reverse mode is the same class of cosmetic known-limitation as the existing high-end seam, not a new crash risk. Net effect on `play_loop~.pd`: its existing bang-retrigger-to-phase-0 mechanism, completely unchanged, already produces correct reverse playback when given a negative `rate` — the first captured sample after a reverse retrigger reads the loop-start value for exactly one sample (a single-sample artifact, same category as the interpolation seam) before jumping to loop-end and descending cleanly from there. Verified end-to-end against real loaded audio through the actual abstraction, not just `phasor~` in isolation: `mlrv-pd/tests/run_play_loop_reverse_test.sh` (correlation 1.000000 against the reversed ramp, mean error 0.001%). Also confirmed the whole call chain leaves `rate` unclamped: `sample_voice~.pd`'s unpack/pack reorder and `file_poly.pd`'s `play`/`playv` dispatch apply `max 0`/`min 7` only to the slot number, never to rate — reverse playback needed zero plumbing changes anywhere, it was a caller-convention gap, not a missing feature.

22. **Pd silently ignores command-line flags placed AFTER the patch file argument — no error either way, the flag just has no effect.** `pd -nogui file.pd` correctly suppresses the GUI (probe-verified: no `wish`/Tk process spawns); `pd file.pd -nogui` does not (a `wish` process spawns exactly as if `-nogui` had never been passed) — same binary, same flag, only the argument order differs. Bit two files in this port the same way, independently: `run_mlrv.sh`'s `exec pd -path ... mlrv-pd/mlrv.pd "$@"` and the AppImage packaging's original `AppRun` (`mlrv-pd/package/`) both appended forwarded flags after the patch filename, so `run_mlrv.sh -nogui`'s own documented usage had never actually worked. Fix: put `"$@"` (or any flags you want honored) before the file argument in any launcher script, not after.

23. **A `[float]` store on the query path must be written silently (right inlet) and read by bang (left inlet) — getting either wrong corrupts state or sprays spurious reports.** Two real bugs from building `mixer.pd`'s query, both caught by its suite, not inspection: (a) wiring the slot number into the store's *left* inlet overwrote every gain with its own slot index (query then reported `vol 1 1`, `vol 2 2` — correct-looking for slot 1, wrong everywhere else); the store needs a bang there, i.e. a `[t b f]` that fans the slot const to the pack's cold inlet and a bang to the store. (b) Tapping control receipts into the store's *left* inlet re-emitted every value, and that emission fired the report pack with a stale cold slot — every `vol`/`send` set leaked a bogus query-shaped line out the info outlet. Right inlet stores silently (the `slot_holder` pattern from Turn 11); left inlet is bang-to-read only. The same rule in one line: stores never sit on a hot inlet, and nothing downstream of a store may fire on a store-write.

24. **A mixed-type `[t]`'s outlet-TYPE order matches the written order (`[t b f]`: outlet0=bang, outlet1=float) — but its FIRING order is still strictly right-to-left regardless of type (gotcha #4 applies unchanged).** These are two independent axes and it's easy to conflate them: "which outlet is which type" (written order, outlet0 first) says nothing about "which outlet fires first" (always rightmost first). Building `file_poly.pd`'s `groupstop` message, a `[t b f]` was wired backwards on BOTH axes in the first draft — the float landed on a msg box (which any message triggers, not just bang, so this half silently "worked" and masked the bug) and the bang landed on a multi-inlet `[expr]`'s hot inlet (which evaluated using `$i1`'s uninitialized default of 0, so the comparison it drove was silently always false — no error, just a feature that mechanically never fired). Caught only by comparing real captured audio against a hand-derived expected sum, not by inspection or a clean load; root-caused with a two-line isolated probe (`[t b f]` -> two `[print]`s, read which one printed first). Probe-verify outlet type AND firing order together for any mixed-type `[t]`, don't assume type-order implies firing-order.

25. **Fan-out from one outlet to multiple destinations is processed depth-first in CONNECTION-CREATION order, not "all destinations get the value simultaneously" — and a bare `[t b b]` silently discards the actual value, re-emitting only a bang.** Two distinct real bugs hit building `sample_voice~.pd`'s `mode shot` duration-timer (Turn 22): (1) `unpack`'s rate outlet fanned out to both the existing pitch-multiply chain and a new duration-calc chain; because the pitch-multiply connection was written into the file FIRST, Pd fully processed that entire downstream chain (all the way through to the play-trigger's mode-check bang) before ever reaching the second connection — so the mode-check read a stale, not-yet-computed duration on every single play. Fixed by inserting an explicit `[t f f]` between the fan-out point and its two consumers, so firing order is controlled directly (right-to-left, gotcha #4) instead of left to implicit connection-creation order. (2) The first attempt at that fix used `[t b b]` instead of `[t f f]` — a bang-type trigger drops the incoming float entirely and just re-emits a bang on each outlet, so the pitch-multiply object received a bang (re-using its stale hot-inlet value) instead of the fresh rate, freezing playback near-silent. Both caught the same way: real captured audio showing exactly the wrong shape (frozen/near-zero instead of a moving ramp), not a load error — the file loaded clean both times. Lesson: never rely on unlabeled outlet fan-out order when it matters, use an explicit `[t]`; and always double-check a `[t]`'s outlet TYPES match what's actually needed, not just its arity.

26. **[qlist]'s two documented playback mechanisms are not equally reliable in this Pd install — and a stored "read" value's own consumer must obey gotcha #23, which it's easy to forget applies to state machines generally, not just query caches.** Three separate findings while building `pattern_recorder.pd`'s auto-loop playback: (a) qlist's *numeric-list-output* mechanism ("a message starting with one or more numbers is output as a list" — the help text's own words) reproducibly failed to fire during auto ([bang]-triggered) playback, across every variation tried (`add`-built vs. file-`read`, single vs. multi-event, zero vs. nonzero delay, DSP on vs. off) — always jumping straight to the done-bang with intermediate events silently skipped, while manual single-stepping (`next`) showed them correctly. The *symbol-prefixed message sent via `[send]`/`[receive]`* mechanism (the one Pd's own bundled `D13.additive.qlist.pd` example actually uses) worked correctly under auto-play with correct relative timing — use that one, not the numeric-list one, for anything that needs to survive `bang`. (b) `[symbol somename\$N]` does NOT work like `[float N]`'s creation-arg-as-default pattern, and does NOT support concatenating a creation arg into a longer literal string the way `[send]`/`[receive]` object-box creation args do — probed directly (`[symbol foo]`, banged, produces no output at all; Pd's own `dollarsign2.pd` reference shows the *only* supported form is a bare `[symbol \$1]`, emitting just the creation arg itself as a runtime atom). A qlist `add`-message needing a per-instance receiver name therefore can't be built this way; a single shared name was used instead as a documented MVP limitation (only one active `pattern_recorder.pd` instance is safe at a time) rather than half-solving it. (c) The classic Pd counter idiom (bang a `[float]` to re-emit its current value, add 1, store the result back) causes a genuine infinite feedback loop (`error: stack overflow`, observed reaching count 498 within one test run) if the incremented result is stored back via the float's HOT inlet instead of its COLD one — this is gotcha #23's "stores never sit on a hot inlet" rule, still true even for a plain counter that has nothing to do with a query cache; storing via the cold inlet fixed it immediately.

27. **[gate]** does not exist in vanilla Pd 0.56.5 — `[spigot]` (or a spigot pair) is the gate.** Probed directly while building mapping.pd's slave wiring: `[gate 2]` fails with `error: ... couldn't create`. A single `[spigot]` passes its hot-inlet message through unchanged when its cold inlet is nonzero and blocks it when 0 (probe-verified: `0` then data was blocked, `1` then data passed, exactly one print). For routing one message down exactly one of two paths based on a stored flag, use a spigot pair with complementary controls (computed on the first-firing outlet of an explicit `[t]`, data delivered on the second — gotcha 25's own fix pattern makes the control-before-data order airtight). Related, same session: a `[pack f f f f f]` cold-fills via inlets 1-4 with no premature emit, and a bare bang to hot inlet 0 re-emits the full stored list (probe-verified: `0 11 22 33 44`) — this is the pending-message store idiom, but remember the atoms sit one position right of a 4-inlet pack, so a message template copied from a 4-inlet context (`play $2 $4 $1 $3`) reads shifted garbage and must be rewritten (`play $3 $5 $2 $4`) — caught by comparing real output against hand-derived values, not inspection.

28. **One store outlet fanning to multiple HOT inlets fires ALL of them on every re-emit — give each hot consumer its own stash.** Third variation of the gotcha-4/25 family, hit building `mapper.pd`'s bind cascade: one `[float]` stash re-emitted into three hot inlets (two pack hots + one `+` hot) executed all three writes on every one of three sequencer steps (triple prints, triple idempotent rewrites, plus phantom dispatches when one of the shared outlets also fed the dispatch read chain). Fix: one stash float per hot consumer (silent cold-fill fan-in stays free), and never let a bind-phase re-emit touch the dispatch read outlet — the bind path got its own dedicated source stash. Same session, same file, gotcha-13's cousin: a `[pack]` feeding `[tabwrite]` must emit `[value index]`, and when the value needs arithmetic (`srcid+1`) it's easy to wire the result into the wrong pack inlet — the write then lands out of range, which is a **silent no-op** (no error), so the table reads back 0 and clear/dispatch silently break while the report prints look exactly right. Caught by tapping the pack's actual output (`[1 17]` instead of `[17 1]`), not by re-reading the wiring.

29. **A bare `[tabwrite~]` with no array argument captures nothing, silently.** It needs its target array as a creation argument (`[tabwrite~ gui_capA]`), exactly like `[tabread4~ $1]` needs its table — an argument-less `[tabwrite~]` loads clean, accepts signal and arm-bangs without complaint, and writes zeros (the table stays untouched, so the capture reads back all-silence). Hit in a test rig, not an abstraction (three captures, two named + one bare — the bare one read back peak 0 while its siblings read 8000). Same family as gotcha 11 (tabwrite~ needs its bang) and gotcha 18: every capture needs signal + arm-bang + NAMED array, all three, or silence with no error. Also new this turn, builder-failure flavor: vanilla Pd has NO `[udpreceive]` (probed: `couldn't create` even with a literal port — use `[netreceive -u -b]` like serialosc.pd, per the established protocol decision); and `[print]` has no outlets (fan out BEFORE it, and unescaped `;` in a comment near it produces the classic gotcha-5 cascade).

30. **A `[text]` with an unescaped `,` truncates the line and silently drops every object after it — including outlet definitions, so later outlets never exist and every connection to them fails with "cannot connect to non-existing object" while earlier connections still look clean.** Classic gotcha-5 but with a new consequence: a long comment containing ", mirrors" without "\," caused Pd to split the line at the comma, treat the remainder as a new object ("mirrors gain/pitch's..."), fail with "canvas: no method for 'mirrors'" and "$1: argument number out of range", and stop parsing before reaching the 4 per-voice outlet~ definitions that followed it — so file_poly loaded clean for the first 2 outlets but the last 2 never existed, and every external patch trying to use outlets 2-5 got "cannot connect" for the last one. Fix: escape every `,` as "\," and every `$` as "\$" even inside `[text]` (same rule as gotchas 1 and 5), and keep per-file comments short; the per-voice outlets fix was simply shortening the comment to one line and putting the text before the outlets in file order (gotcha 7's "objects before connects" plus this).

### Protocol decisions specific to this port

- **No `monome-device` external dependency.** `serialosc.pd` talks to the `serialosc` daemon directly over UDP (`netsend`/`netreceive` with `-u -b`, `oscformat`/`oscparse`) against the wire protocol `mlrv2/code/serialosc.js` documents: daemon on `127.0.0.1:12002`, `/serialosc/list` + `/serialosc/notify` to discover/subscribe, `/serialosc/device` replies give each device's own OSC port, and `/sys/port` + `/sys/prefix` sent to that device's port complete the handshake.
- **No `port + 12288` offset scheme.** The original `serialosc.js` computes its listen port as `arguments[0] + 12288`, purely as its own internal bookkeeping convention — the `serialosc` daemon itself doesn't require or care about this offset. This port drops it: `serialosc.pd`'s port creation argument is the literal port to bind and advertise, full stop (see gotcha 6 above for why the offset can't be replicated faithfully in Pd anyway).
- **`play_loop~.pd`** is the shared loop-playback abstraction every sample voice reuses: `phasor~` (0–1 ramp) → scaled into `[loopStart, loopEnd)` via control-rate arithmetic → `tabread4~`. Its single control inlet takes either `bang` (retrigger from loop start) or a 3-element list `rate loopEndSamples loopStartSamples` for an atomic parameter update — this relies on Pd's `unpack` firing right-to-left, which is why the list argument order matters and isn't arbitrary. Known limitation, undocumented workaround: `tabread4~`'s 4-point interpolation window can read ~2 samples outside the loop bounds at the seam (no crossfade).

Not yet reachable from `mapping.pd`/the grid (same reachability gap as reverse/gain/pitch), and slots cancelled by exclusivity don't currently reset their own `mlrv-fpvgroup` entry to 0 (harmless today — a re-stopped voice is still just stopped — but worth knowing if `mlrv-fpvgroup` is ever read for anything beyond exclusivity/groupstop).

**Tempo/quantize/slave (1:1 `trentgill/mlrv` recreation track, item 2): new `mlrv-pd/abstractions/clock.pd`, a from-scratch tempo/quantize subsystem — built and verified independently of the mute-groups work, deliberately not wired into `file_poly.pd`/`mapping.pd`/`sample_voice~.pd` yet.** `trentgill/mlrv`'s own `time.maxpat` builds this on Max's `[transport]` object plus symbolic time syntax (`4n`/`16n`/`32n`, note-values that auto-scale with tempo) — Pd has no equivalent to either, so this is genuinely new architecture, not a port of an existing Pd mechanism. Scope deliberately narrow: internal tempo/quantize only — no MIDI clock, no audio-sync, no tilt-tempo (all present in the original's `time.maxpat`, none needed here: no MIDI hardware or audio-sync source exists in this Pd port's context, and this port has never touched MIDI).

Interface: `tempo <bpm>` (default 120), `quantize <beats>` (default 1 — the grid size a trigger gets held to), a bare `bang` (a trigger to be quantize-gated: held until the next grid boundary, then released as a bang on outlet 0). Outlet 1 taps the raw beat-pulse `[metro]` directly, for free, for future use (e.g. LED sync). Mechanism, probe-verified in isolation *before* being written into the real abstraction (matching this port's established discipline): a `[float 0]` "pending" store, banged to re-emit by the metro's own tick, gated through `[sel 1]` and reset — the same store/bang-to-read/reset idiom already used throughout this port (mixer.pd's query, sample_voice~.pd's gain, file_poly.pd's group exclusivity). Verified against real elapsed time via Pd's own `[timer]`, not just message-arrival order: 120bpm + quantize 1 beat = 500ms grid; a trigger fired 220ms after load was released exactly 280ms later (at the 500ms boundary) — reproduced identically across 3 consecutive runs, no timing jitter observed under `pd -nogui`. `mlrv-pd/tests/run_clock_test.sh` is its regression suite.

The interval-recompute path (`[t b f]` feeding the multiply that combines ms-per-beat with quantize-beats) was wired with the same type-vs-firing-order care as gotcha #24, learned one abstraction earlier the hard way — no repeat of that bug here.

**Deliberately deferred, not because it's hard but because it was genuinely ambiguous without its own dedicated probe**: verifying a tempo *change* mid-flight against `[metro]`'s own interval-change semantics (does a new interval affect the tick already pending, or only subsequent gaps?). Rather than assert an unverified behavior, the test only covers the default-tempo scenario; a future task should probe `[metro]`'s rescheduling behavior specifically before building anything that depends on it (e.g. a live tempo-nudge feature).

**Integration point for a future `slave` feature, documented but not built**: a channel's trigger should be sent into `clock.pd`'s inlet instead of directly to `file_poly.pd`'s `play`/`playv` dispatch when that channel's `slave` flag is set; the released bang on outlet 0 is what should actually fire the play. This requires `file_poly.pd`/`mapping.pd` changes (routing a triggered channel's bang through `clock.pd` conditionally on its `slave` state) that were out of scope for this task specifically to avoid a file collision with concurrent mute-groups/SHOT-mode work on those same files.

**`slave` wiring DONE (Turn 23, this session) — item 2 complete.** `mapping.pd` now takes `slave <slot 0-7> <0|1>` (stored in new `[table mlrv-mslave 8]`, 0 = immediate default, gated 0..7 via the proven route-0..7 idiom) plus `tempo <bpm>`/`quantize <beats>` (re-tagged and forwarded into a contained `[clock]`, since `route` strips the selector). Trigger gating taps pack20's `(start slot end rate)` output through `[t l l]`: outlet 1 (first) reads the slot flag and pre-sets a spigot pair (immediate vs held — gotcha #27, `[gate]` doesn't exist); outlet 0 (second) delivers through exactly one. Held triggers cold-store in a 5-inlet pack and fire on clock.pd's release bang, rebuilt byte-identically as `play <slot> <rate> <start> <end>` (last-write-wins on retrigger; LED stays immediate as press-ack; new outlet 2 exposes clock.pd's beat pulse). Verified against real elapsed time: slaved release exactly 280ms after a 220ms-delayed press (mirrors the clock suite's own 260-300 window), 3x unslaved/immediate cases at 0ms, tempo 240 → steady 250ms beat intervals, quantize 2 → steady 500ms (`mlrv-pd/tests/run_mapping_slave_test.sh`, 7/7). Built via `tests/builders/extend_mapping_slave.py` (+ a one-line-template follow-up fix, `extend_mapping_slave_fixmsg.py`) and `tests/builders/build_test_mapping_slave.py`. Known limits, documented not hidden: stopall doesn't cancel a held trigger; direct `file_poly.pd` play messages are never gated (grid path only); no grid gesture sets slave/tempo/quantize yet.

**Two latent `clock.pd` bugs found and fixed by the slave test (both invisible to the original clock suite, which never observes outlet 1 or sends tempo):** (1) the tempo path never refreshed the mult's quantize factor (cold-init 0, probed) — the first real `tempo` receipt computed interval 0 and flooded a running metro (~360-750 ticks/sec observed); fixed by routing tempo receipts through `[t f b]` so the stored factor is re-emitted before tempo recomputes (`tests/builders/extend_clock_tempo.py`). (2) Worse, the load-time compute had ALWAYS written interval 0 (same cold-init 0) — masked only because Pd's metro schedules its next tick with the new interval, so the pending 500ms first tick still fired on time (release timing looked perfect) while every tick after it rescheduled immediately; fixed by having loadbang seed `[float 1]` (which re-emits through the existing `[t b f]`, computing the correct 500 x 1 = 500 before any tick can fire) instead of banging `[float 120]` directly (`tests/builders/extend_clock_load.py`). Standalone flood-check before: 3484 beats + 1 release in 4s; after: 8 beats + 1 release. The original suite's "no timing jitter" claim survives — but only the release path was ever actually verified before this.

**Mapping engine (1:1 `trentgill/mlrv` recreation track, item 5 mapping GUI, increment 1 of 2): new `mlrv-pd/abstractions/mapper.pd`, the binding core a literal Pd GUI will sit on — built and verified, no GUI widgets yet.** Model: every mappable endpoint is a flat-symbol PARAM; external controls arrive normalized as `ctl <class> <id> <val01>` (class 0=MIDI 1=OSC 2=KEY — adapters are increment 2; increment 1 tests send `ctl` directly). `learn <sym>` arms; the next ctl binds (stealing the source); otherwise ctl dispatches with per-param min/max scaling. `min/max/clear <sym>` edit/remove. Outlet 0 = engine messages, outlet 1 = reports. Identity packs to one int (`srcid = class*128+id`); `fwd[param]=srcid+1` / `rev[srcid]=paramidx+1` tables (0 = unbound = zero-init). Four param kinds: cont, dint, dsym (int 0/1 selects two symbol messages), trig (fixed message on any ctl). Increment 1 covers 7 params (tempo, master, vol0, vgain1, vmode1, sgroup0, groupstop1) via a parameterized generator (`mlrv-pd/tests/builders/build_mapper.py`, fresh-build, refuses twice) so increment 2 is a table extension, not a rewrite.

Verified message-exact (mapper's contract is control-plane): learn/bind/steal/dispatch/min-edit/clear/unbound-drop plus clamp and dsym selection — `mlrv-pd/tests/run_mapper_test.sh`, 12/12. Full audio end-to-end (widget → engine → captured sound) belongs to increment 2.

Three real bugs building it, all caught by running: (1) `[t b b b]` for per-param ordering dropped the value at the hot inlet (gotcha 25 again — `[t f f f]` keeps it); the first suite's expectations were then found to have been written against the buggy phantom-dispatch behavior (bind-time firing), not the design — fixed the TEST, including an `int()`-truncation expectation (0.9 → 0 is correct; shot needs 1.0). (2) Shared stash outlet → 3 hot inlets (gotcha #28). (3) pack/tabwrite atom order (gotcha #28's cousin). New builder-failure mode worth knowing: wiring a message straight into a `[table]` fails at load (`message->canvas connection failed`) — tables need `[tabwrite]` objects, same as everywhere else; and `[print]` has no outlets (fan out before it, not through it) — both of these bit throwaway /tmp probes this session too, not just the real file.

**Increment 2 DONE (Turn 25, this session): the literal GUI.** `mapper_params.py` (shared PARAMS table — single source of truth for engine formats, imported by both builders so widgets and dispatch can never drift); 50 params. **Live audio recording (1:1 `trentgill/mlrv` recreation track): new `mlrv-pd/abstractions/record_buffer~.pd` — built and verified independently, deliberately never touching `play_loop~.pd`/`sample_voice~.pd`/`file_poly.pd`/`mapping.pd`.** Key design decision that shrank this item's real scope: playback of a finished recording deliberately reuses those four files *unchanged* — a recorded buffer is just an array, playable through the exact `set <arrayname>` mechanism any loaded sample already uses, so this item only had to build the *recording* half. Max's `[record~]` maps directly onto Pd's `[tabwrite~]` (gotchas #11, #17), fed by whatever signal the caller wires into the signal inlet (`adc~` for live input, a `dac~` tap for resampling — matching the original's "live audio input (or resampled audio output)"). Interface: bare bang or `record` (equivalent) arms recording after any pending preroll; `loop <0|1>` auto-rearms on completion for continual overwrite recording (preroll applies only to the first arm, not later loop iterations); `preroll <ms>` delays the actual start; outlet1 = done bang. `duration_ms = arraySize / sampleRate * 1000` is computed once at load (`[array size $1]`/`[samplerate~]`, never trusted from a caller — same reasoning as gotcha #8) rather than re-derived per recording, since neither value changes mid-run.

Verified against real captured audio and real timing: a bare bang and the word `record` both capture real `osc~` content, not silence; preroll correctly delays the start (array is silent before the delay elapses, has real signal after); loop mode auto-rearms at the correct rate (settled count ~109 over ~1s of a ~9.19ms cycle, matching the hand-derived expectation almost exactly). `mlrv-pd/tests/run_record_buffer_test.sh`.

**A long, entirely self-inflicted debugging detour worth recording, even though it found no real bug in the abstraction**: the loop-mode count initially looked wrong by roughly 2x. Chased through a broken self-feedback `[+ 1]` counter idiom (feeding an object's own output back into its own HOT inlet creates a same-tick runaway loop; the correct idiom is `[f]`+`[+ 1]` with the increment fed back into `[f]`'s COLD inlet only), then a `[realtime]` object that produced no output for reasons never resolved (abandoned), before finding the actual cause: a shell-level `timeout` wrapper was killing the test process well after the intended measurement window, and since nothing was explicitly stopping the internal loop or its counter, the "final" printed count reflected the whole process lifetime, not the ~1000ms window intended. Confirmed via a bare, non-abstraction `[delay]` retriggering at the same rate outside any wrapper, which showed the correct rate all along. Fixed by having the test explicitly send `loop 0` to stop the count from growing before reading it, instead of racing an external process kill. Not a new gotcha here (the bug was in test methodology, not a non-obvious Pd behavior) — but worth remembering that a suspicious count is worth checking the *test's* stop condition before assuming the *abstraction* is wrong.

**Pattern recorders (1:1 `trentgill/mlrv` recreation track, item 3): new `mlrv-pd/abstractions/pattern_recorder.pd` — built and verified independently, deliberately never touching `play_loop~.pd`/`sample_voice~.pd`/`file_poly.pd`/`mapping.pd`.** Sourced from `trentgill/mlrv`'s own docs: "when armed, the pattern recorder will wait until a button is pressed, then immediately begin to record button presses until it reaches the end of its recording buffer. then and there, the pattern will begin to playback automatically... patterns may be silenced by simply pressing the trigger button." MVP scope: recording length is taken directly in `length <ms>`, not bars (converting bars to ms via `clock.pd`'s tempo is a caller's job — this abstraction doesn't depend on `clock.pd` at all). Overdub is explicitly NOT built — a real, separate design question, not guessed at.

Mechanism: `[qlist]`, used the way Pd's own bundled example uses it (symbol-prefixed messages via `[send]`/`[receive]`, not qlist's numeric-list-output outlet — see gotcha #26 for the full probe trail behind that choice). qlist's delay-per-entry is relative to the previous entry, not an absolute offset from playback start (confirmed against Pd's own bundled `qlist.txt`) — recording tracks "ms since the last recorded event" via a `[timer]` reset after every `add`, not "ms since recording started." Interface: `arm` (wait for first live event, clears any existing pattern), a bare `list x y state` (a live grid event — always passed through to outlet 1 unconditionally, real-time performance is never blocked by the recorder; captured into the pattern only while armed/recording), `length <ms>` (default 4000), `stop` (silence playback), `play` (resume), `clear` (delete). Outlet 0: `list x y state` during playback.

**Real bug caught and fixed, distinct from the qlist findings**: `state` (the 0=idle/1=armed/2=recording/3=playing/4=stopped store) was originally wired with its "set new value" messages landing on its HOT inlet, same as its "bang to re-read current value" call sites — this is exactly gotcha #23's rule violated on a state machine, not just a query cache, and caused a genuine feedback loop (setting state to "recording" immediately re-triggered the recording-check branch with stale/zero pack data, producing garbage `add` entries at load time before any real event occurred). Fixed by moving every "set" message to `state`'s COLD inlet, leaving only the two legitimate "bang to check" call sites (a live event's own arrival, and qlist's done-bang for the loop-check) on the hot inlet.

Verified against real elapsed time and real event content, not just message order: recorded two live events 100ms apart with `length 300`; both passed through live immediately; auto-stop-and-playback started at exactly 400ms (300 length + 100 event1 offset); playback content and order matched the recording exactly; looping is seamless (a new lap's first event lands at the exact same instant the previous lap's last event fired, since qlist's done-bang has no built-in trailing gap — confirmed empirically, not assumed); `stop` halted playback immediately mid-lap rather than finishing it. `mlrv-pd/tests/run_pattern_recorder_test.sh`, stable across repeated runs (no timing jitter observed under `pd -nogui`).

**Known limitation, documented not hidden**: only one active instance is safe at a time (see gotcha #26b for why per-instance qlist send/receive naming didn't work out as originally planned).

## Packaging: standalone executable (`mlrv-pd/package/`)

Started Turn 22, a new task track parallel to (not blocking) the port-completeness work above: a self-contained, double-clickable Linux x86_64 AppImage of `mlrv-pd`, so end users don't need a separate Pd install. `mlrv-pd/package/build_appimage.sh` builds it: bundles a local `pd` install's binary + its `lib/pd` support directory (the "extra" objects like `expr`, doc, tcl GUI files) alongside this port's `abstractions`/`patchers`/`samples`, using `linuxdeploy` (downloaded on first run, gitignored) to assemble and package the AppImage. Source templates (`AppRun.src`, `mlrv.desktop.src`, `mlrv.png.src`) are checked in; `AppDir/`, `linuxdeploy`, and `*.AppImage` are build output, gitignored.

**Verified genuinely end-to-end, not just "it launches"**: ran the packaged bundle's own `pd` binary (not the dev environment's) against its own bundled abstractions (not the dev tree's) through the existing `test_mlrv.pd` fake-daemon harness — real captured audio matched the expected gain+tanh math exactly (peak 14321 vs. expected 14325.8), and the LED feedback command fired correctly. Confirmed the resulting `.AppImage` file itself (not just the unpacked `AppDir`) actually self-mounts via FUSE and runs the real `pd` process with correctly-resolved bundled paths — checked via the live process list, not just a clean exit code.

Uncovered gotcha #22 while building `AppRun` (see above) — the same bug had been silently present in `run_mlrv.sh` since Turn 16, now fixed in both places.

This delivers "standalone executable" for what `mlrv-pd` already covers (grid-controlled sample playback, no on-screen UI). It does **not** yet address the much larger scope of a true 1:1 `trentgill/mlrv` recreation — see the Obsidian planning doc `mlrv-pd — 1:1 mlrv Recreation and Packaging` for the full feature-gap analysis (pattern recorders, live audio recording buffers, mute groups, MIDI/OSC/keyboard mapping with a GUI, delay/aux effects, tempo/quantize/slave sync, JSON presets) sourced from both `trentgill/mlrv`'s actual repo and its own "2.1 preliminary documentation" (including a complete OSC address spec).
